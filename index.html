01 BeBig · 문제상황 / 목표

제가 해결해야 한 문제는 금융 데이터를 사용자가 행동으로 이해하게 만드는 것이었습니다.

BeBig 2/3
문제상황

계좌·거래 데이터를 화면에 그대로 노출하면 사용자가 다음 행동을 알기 어렵다

  • 계좌와 거래 내역 API 응답을 화면에 그대로 뿌리면 사용자가 소비 패턴과 개선 행동을 해석해야 했습니다.
  • CODEF 계좌 연결은 민감한 금융 정보 입력과 긴 대기 시간이 있어 진행 상태 안내가 필요했습니다.
  • 거래 내역은 데이터 양이 많아 무한 스크롤, 날짜 그룹핑, 입출금 시각 구분이 없으면 모바일 가독성이 떨어졌습니다.
목표

계좌 연결, 분석, 미션, 추천을 하나의 화면 흐름으로 연결하기

  • CODEF 계좌 데이터를 자산 분석, 소비 분석, 미션, 상품 추천에서 재사용할 수 있도록 화면/API 흐름을 정리했습니다.
  • 계좌 연결 단계마다 로딩 문구, 오류 횟수, 완료 계좌 목록을 제공해 사용자가 진행 상태를 이해하게 했습니다.
  • 숫자 데이터는 차트, 문장 피드백, 카드, 캐릭터, 뱃지로 바꿔 행동 유도형 UX로 구성했습니다.

자산 분석소비 차트, 평균 비교, 상품 추천

01 BeBig · 해결책 / 성과

금융 데이터를 읽히는 화면과 반복 사용 동기로 바꿨습니다.

BeBig 3/3

해결책

  • Vue Router를 도메인별로 분리해 홈, 자산, 미션, 커뮤니티, 마이페이지 진입 흐름을 명확히 구성했습니다.
  • Pinia와 LocalStorage로 로그인 상태, 은행 선택, 커뮤니티 페이지 상태를 유지했습니다.
  • Axios Interceptor와 refresh token 확인 로직으로 인증 실패 시 사용자가 어색한 화면에 남지 않게 처리했습니다.
  • 계좌 연결은 단계별 로딩 메시지와 오류 안내로 민감한 입력 과정의 불안을 줄였습니다.
  • 거래 내역은 무한 스크롤과 날짜별 그룹핑, 입출금 색상 구분으로 읽기 쉽게 구성했습니다.
  • 금융 유형 검사는 질문 랜덤화, 월수입 질문 고정, 숫자 검증, 금액 포맷팅, 유형 산출 로직을 화면에서 일관되게 처리했습니다.
  • 자산 분석은 Chart.js 월별 소비 그래프, 평균선, 전월 대비 문장 피드백, 주거래 은행 기반 상품 추천 캐러셀로 구성했습니다.

성과

  • 실제 계좌 데이터가 자산 분석, 미션, 상품 추천, 커뮤니티로 이어지는 사용자 흐름을 완성했습니다.
  • PM으로 Jira, Notion, Figma, Git Flow, PR 리뷰 기준을 운영해 팀 협업 비용을 줄였습니다.
  • 프론트엔드에서 단순 조회가 아니라 사용자가 다음 행동을 이해하는 금융 UX를 구현했습니다.

03 Newstagram · 개요 / 역할

RSS 뉴스 수집부터 AI 추천까지 연결한 뉴스 큐레이션 서비스

Newstagram 1/4
개요

실시간 이슈와 개인화 뉴스를 제공

여러 언론사의 RSS 기사를 수집하고, 기사 임베딩과 사용자 행동 로그를 기반으로 실시간 이슈, 개인화 추천, 자연어 프롬프트 검색을 제공했습니다.

역할

PM · Backend · Frontend

PM으로 기능 우선순위와 서버 구조를 잡고, Backend에서는 RSS/임베딩/클러스터링/로그 파이프라인을, Frontend에서는 주요 뉴스 화면과 API 연동을 구현했습니다.

Spring Batch Quartz PostgreSQL · PgVector Kafka Vue 3 DBSCAN
수집/임베딩

RSS entry 정규화, 썸네일 추출, 중복 URL skip, 1536차원 기사 임베딩 저장을 구현했습니다.

추천 파이프라인

DBSCAN 이슈 클러스터링, PgVector 유사도 검색, Kafka 클릭 로그 기반 선호 벡터 갱신을 연결했습니다.

화면/API 조율

핫이슈, 프롬프트 검색, 개인 추천, 기사 클릭 로깅 API를 화면 단위로 계약화했습니다.

우측 대형 이미지 Newstagram 메인 뉴스 피드

이미지 위치: 실시간/일간/주간 핫 이슈 탭과 기사 카드가 보이는 메인 화면. 프로젝트 첫 장에서는 사용자가 보는 결과물을 배치합니다.

03 Newstagram · 문제상황 / 목표

제가 해결해야 한 문제는 외부 뉴스 데이터를 추천 가능한 파이프라인으로 바꾸는 것이었습니다.

Newstagram 2/4
문제상황

RSS, 임베딩, 로그, 추천이 한 흐름으로 이어지지 않으면 기능이 분절된다

  • RSS feed마다 XML 구조, 본문 형식, 썸네일 위치, tracking URL이 달라 정규화 계층이 필요했습니다.
  • 단순 키워드 검색으로는 표현이 다른 유사 기사와 자연어 검색 의도를 처리하기 어려웠습니다.
  • 개인 추천은 클릭 로그가 쌓여야 동작하므로 콜드스타트 사용자에 대한 초기 선호 벡터가 필요했습니다.
  • 외부 RSS와 AI 임베딩 API 실패가 배치 전체 실패로 번지지 않게 feed 단위 처리와 로그가 필요했습니다.
목표

수집, 벡터화, 클러스터링, 로그 기반 추천을 자동화하기

  • 여러 언론사 RSS를 주기적으로 수집하고 URL unique constraint로 중복 저장을 방지했습니다.
  • 기사 내용을 임베딩해 PgVector에 저장하고 DBSCAN으로 유사 기사 클러스터와 이슈 랭킹을 만들었습니다.
  • 기사 클릭 로그는 Kafka로 비동기 수집하고 최근 30개 로그에 시간 감쇠를 적용해 선호 벡터를 갱신했습니다.
  • 프롬프트 검색과 개인 추천은 같은 벡터 검색 기반으로 연결해 기능별 구현 중복을 줄였습니다.

03 Newstagram · 해결책

데이터 파이프라인을 서버 단위로 분리하고 실패를 추적 가능하게 만들었습니다.

Newstagram 3/4

해결책

  • api-server, rss-collector, logging-server, domain 모듈로 역할을 분리했습니다.
  • Rome/Jsoup으로 RSS entry를 Article로 변환하고, 썸네일 추출, HTML 정제, tracking URL 필터링을 처리했습니다.
  • Spring Batch와 Quartz로 RSS 수집, 기사 임베딩, 실시간/일간/주간 클러스터링을 스케줄링했습니다.
  • 기사 임베딩은 PgVector에 저장하고, Smile DBSCAN으로 유사 기사 그룹을 만들었습니다.
  • Kafka 클릭 로그 consumer가 최근 30개 로그에 시간 감쇠를 적용해 사용자 선호 벡터를 갱신했습니다.
  • Redis look-aside cache와 system job log로 조회 비용과 운영 추적성을 개선했습니다.
  • 임베딩은 제목/본문 정규화 후 batch 단위로 호출하고, 1536차원 PgVector literal로 변환해 저장했습니다.
  • Kafka DLT, feed 단위 skip, API 응답 개수 불일치 로깅으로 외부 RSS/AI 실패가 전체 배치를 멈추지 않도록 했습니다.
우측 대형 도식 Newstagram 전체 시스템 아키텍처

이미지 위치: api-server, rss-collector, logging-server, PostgreSQL/PgVector, Kafka, Redis가 연결된 구조도. 데이터 파이프라인 설명 슬라이드의 핵심 보조 자료입니다.

04 A601 · 개요 / 역할

WebRTC와 WebSocket으로 완성한 실시간 AI 마피아 게임

A601 1/4
개요

AI 판사가 지배하는 SF 서바이벌 게임

A601은 실시간 영상/음성 대화와 게임 이벤트를 결합하고, 플레이어 변론을 AI가 분석해 처형 대상을 결정하는 웹 기반 마피아 게임입니다.

역할

PM · Frontend · 실시간 UX

PM으로 게임 루프와 협업 컨벤션을 정리했고, Frontend에서 LiveKit, STOMP, Zustand 기반 실시간 게임 화면과 단계 전환을 구현했습니다.

React Zustand LiveKit WebRTC STOMP/SockJS AI Judge
실시간 연결

LiveKit Room 연결과 STOMP 구독/발행을 분리하고 LobbyShell에서 진입/이탈을 통합 처리했습니다.

게임 상태

Zustand slice와 StageRouter로 lobby, role, day, ai, judgment, night, result 전환을 관리했습니다.

예외 UX

AI 판결 지연, 미제출자, 사망자 권한, 밤 페이즈 시청 권한, 방장/준비 상태를 화면에 반영했습니다.

우측 대형 이미지 A601 대표 게임 화면

이미지 위치: SF 콘셉트가 보이는 인게임 화면 또는 대기방 화면. 첫 장에서는 실시간 영상 게임이라는 인상이 바로 드러나야 합니다.

04 A601 · 문제상황 / 목표

제가 해결해야 한 문제는 영상 연결과 게임 상태를 동시에 안정화하는 것이었습니다.

A601 2/4
문제상황

미디어 권한과 게임 이벤트가 따로 움직이면 phase 전환이 깨진다

  • 낮, 밤, AI 판결, 사망 상태마다 영상/음성 publish/subscribe 권한과 UI 상호작용이 달라져야 했습니다.
  • WebSocket 메시지 순서가 꼬이면 AI 판결 화면이 생략되거나 다음 phase가 먼저 노출될 수 있었습니다.
  • AI 판결 API 지연, 변론 미제출자, 연결 끊김이 있어도 게임 루프가 멈추지 않아야 했습니다.
목표

서버 권위 상태를 기준으로 클라이언트 stage와 권한을 동기화하기

  • 영상/음성은 LiveKit WebRTC, 게임 이벤트는 STOMP WebSocket으로 역할을 분리했습니다.
  • 서버 권위 상태를 기준으로 클라이언트 stage, 타이머, 직업 능력, 영상 타일 상태를 반영했습니다.
  • AI 판결이 늦어져도 pending stage queue로 대기 연출 후 결과 화면과 다음 phase를 순서대로 보여줬습니다.

04 A601 · 해결책

미디어 권한, 게임 이벤트, 화면 stage를 분리해 제어했습니다.

A601 3/4

해결책

  • LobbyShell에서 LiveKit Room 연결, STOMP 연결, 방 메타 조회, stage 라우팅, disconnect 처리를 통합했습니다.
  • StageRouter로 lobby, role, morning, ai, waiting, judgment, night, result, ending 화면을 분리했습니다.
  • Zustand를 roomSlice, lobbySlice, inGameSlice로 나눠 입장 정보, 게임 상태, UI 상태를 분리했습니다.
  • GAME_PHASE와 AI_RESULT 처리를 분리하고, pending stage queue로 판결 연출 후 다음 단계가 반영되게 했습니다.
  • 사망자, 외계인 밤 권한, CCTV 결과, 보호 대상, 타겟 확정 상태를 영상 타일 UI에 반영했습니다.
  • 낮/밤/사망자 상태에 따라 LiveKit publish/subscribe 권한과 STOMP 게임 이벤트를 분리해 처리했습니다.
  • 6인/8인 역할 풀, 방장 권한, 준비 상태, AI 변론 미제출/지연 같은 예외를 화면 상태로 흡수했습니다.
우측 대형 도식 WebRTC / WebSocket 분리 아키텍처

이미지 위치: Frontend, Spring Backend, Redis, LiveKit Server, AI Server가 연결된 구조도. 영상/음성과 게임 이벤트를 분리한 판단을 설명하는 위치입니다.

05 용돈농장 · 개요 / 역할

청소년 금융 활동을 실제 돈의 흐름처럼 경험하게 한 교육 플랫폼

용돈농장 1/4
개요

용돈, 예적금, 일과, 대출, 신용점수

용돈농장은 학생이 소비, 저축, 대출, 상환, 신용 관리를 작게 경험하고, 부모가 이를 관리하며 금융 책임을 함께 학습하는 서비스입니다.

역할

Backend 개발

DB 설계, REST API, QueryDSL 조회 최적화, SSAFY 금융 API 연동, 인증/인가, 도메인 비즈니스 로직을 담당했습니다.

Java 21 Spring Boot JPA QueryDSL PostgreSQL Redis SSAFY 금융 API
도메인 모델

사용자/자녀, 예적금, 일과, 대출, 신용점수를 상태와 이력 중심으로 분리해 설계했습니다.

복합 조회

QueryDSL로 가입 가능 상품 우선 정렬, 중복 가입 제외, 커서 페이지네이션, 대시보드 집계를 구현했습니다.

외부 연동

SSAFY 금융 API 요청 생성을 Factory/Client/Validator로 분리하고 인증/인가 흐름과 연결했습니다.

우측 대형 이미지 용돈농장 서비스 대표 화면

문제상황

부모·자녀 권한과 외부 금융 API 상태가 섞이면 정합성이 무너진다

  • 부모와 자녀는 같은 도메인 데이터를 보지만 신청, 승인, 상환, 리뷰 권한이 서로 달라야 했습니다.
  • 예적금, 대출, 일과 보상은 외부 금융 API 호출과 내부 DB 상태 변경이 함께 발생했습니다.
  • 금융 이벤트가 신용점수와 거래 장부로 남지 않으면 사용자가 행동의 결과를 추적하기 어려웠습니다.

금융 행동마다 상태 전환, 거래 장부, 신용점수 이력을 남기기

  • 자녀 신용점수, 평점, 대출 장부, 가입 이력을 별도 테이블로 분리해 추적 가능하게 모델링했습니다.
  • 외부 API 요청 생성과 검증은 Client/Factory 계층으로 분리해 서비스 로직의 도메인 책임을 명확히 했습니다.

06 AutoQA · 개요 / 역할

AI가 실제 브라우저에서 실행 가능한 QA suite를 만드는 플랫폼

AutoQA 1/5
개요

URL 입력부터 결과 리포트까지 자동화

AutoQA는 웹 페이지를 분석하고 AI가 QA 시나리오를 생성한 뒤, Playwright로 자동 실행하고 결과 리포트와 Jira 이슈화를 제공하는 AI QA 자동화 SaaS입니다.

역할

PM · AI

PM으로 비동기 파이프라인과 책임 경계를 설계했고, AI 담당으로 데이터 수집/정제, Qwen3-8B fine-tuning, vLLM 추론, 평가 지표를 구축했습니다.

Qwen3-8B QLoRA · SFT · DPO vLLM Playwright SQS · Redis · S3 PM
PM 구조 설계

PAGE_ANALYSIS, SCENARIO_GENERATE, QA_EXECUTE 단계와 SQS/Redis/S3 책임 경계를 정의했습니다.

AI 데이터

site-summary와 analysis-summary를 compact input으로 압축하고 SFT/DPO 학습 데이터를 정제했습니다.

실행 계약

nodeId, step type, matcher, popup/form/destructive action 정책을 validator와 모델 학습에 반영했습니다.

우측 대형 이미지 AutoQA 메인 또는 QA 리포트 화면

이미지 위치: URL 입력, 진행 상태, QA 결과 리포트 중 하나. 첫 장에서는 URL 입력부터 리포트까지의 자동화 흐름이 바로 보여야 합니다.

06 AutoQA · 문제상황 / 목표

제가 해결해야 한 문제는 AI 출력을 실제 실행 가능한 QA 계약으로 제한하는 것이었습니다.

AutoQA 2/5
문제상황

LLM이 만든 시나리오는 검증 없이는 Playwright 실행기로 보낼 수 없다

  • AI가 존재하지 않는 nodeId를 만들거나 다른 page brief의 요소를 target으로 쓰면 실행 전부터 실패합니다.
  • popup, form, select, maxlength, destructive action 같은 실행 규칙을 지키지 않으면 Playwright step이 깨집니다.
  • 웹 분석 산출물은 raw 기준 token이 매우 커서 그대로는 fine-tuning과 추론 입력으로 사용하기 어려웠습니다.
  • AI 생성 결과를 그대로 실행하면 QA 실패 원인이 모델, locator, 실행기 중 어디인지 분리하기 어렵습니다.
목표

모델, validator, 실행기, 리포트를 분리해 실패 원인을 추적하기

  • AI는 suite JSON 생성만 담당하고, 검증은 Backend validator, 실행은 Playwright Worker가 책임지게 분리했습니다.
  • SQS는 작업 분배, Redis/WebSocket은 실시간 UX, S3는 대용량 산출물 저장으로 역할을 나눴습니다.
  • 모델 평가는 loss뿐 아니라 validator pass, hallucination, contract violation, diversity를 함께 보도록 설계했습니다.
  • 대용량 분석 결과는 SQS payload가 아니라 S3 artifact URL로 넘겨 메시지 크기와 재처리 비용을 제어했습니다.

06 AutoQA · 해결책 / PM Architecture

AI와 실행기를 분리하고, 비동기 파이프라인을 표준화했습니다.

AutoQA 3/5

해결책: 제품 구조

  • PAGE_ANALYSIS -> SCENARIO_GENERATE -> QA_EXECUTE 3단계 표준 파이프라인을 정의했습니다.
  • AI 출력은 Backend validator를 통과해야 사용자 검토 단계로 넘어가게 했습니다.
  • 검증 실패 시 AI 재요청, GMS fixer, drop fallback을 단계별로 적용했습니다.
  • SQS result queue와 Redis state snapshot을 기준으로 최종 상태를 복구할 수 있게 설계했습니다.
  • site-summary 우선 정책으로 AI가 단일 페이지가 아니라 사이트 전체 기능 분포를 보게 했습니다.
  • autoScenarioEligible, confidence score, same-page nodeId 제한, destructive action 금지 정책을 contract와 validator 양쪽에 반영했습니다.
  • Redis Pub/Sub은 화면 이벤트, SQS는 terminal event source of truth로 분리해 실시간 UX와 복구 가능성을 함께 잡았습니다.
우측 대형 도식 SQS / Redis / S3 기반 비동기 아키텍처

이미지 위치: Backend, Playwright Worker, AI Worker, SQS, Redis, S3, WebSocket의 책임 경계가 보이는 구조도. PM 의사결정 설명에 가장 중요한 이미지입니다.

06 AutoQA · 해결책 / AI Pipeline

웹 분석 데이터를 학습 가능한 compact input으로 바꾸고 모델을 고도화했습니다.

AutoQA 4/5

해결책: AI 데이터와 모델

  • raw site-summary와 analysis-summary에서 nodeId, role, purpose, confidence, functional path 중심 compact input을 설계했습니다.
  • avoid_auto_generation, ineligible target, page-target mismatch, nodeId hallucination 사례를 정제했습니다.
  • Gemma4 LoRA/QLoRA 실험의 OOM과 multimodal device map 리스크를 분석하고 Qwen3-8B로 전환했습니다.
  • SFT와 DPO 데이터를 만들고, contract-aware negative pair를 구성했습니다.
  • vLLM과 guided JSON 추론, partial scenario extraction, max_new_tokens 확장으로 긴 JSON 출력 문제를 진단했습니다.
  • 139개 사이트 중 132개가 10K token을 넘는 raw input이어서, key 축약과 후보 cap으로 median 9~10K token compact input을 만들었습니다.
  • SFT 이후에는 validator 실패 패턴을 negative pair로 묶어 DPO 데이터에 반영하고, mode collapse 여부를 별도 점검했습니다.
