| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | BeBig |
| 한 줄 소개 | 금융 공공데이터와 실제 계좌 데이터를 기반으로 사용자의 자산, 소비 패턴, 금융 유형을 분석하고 맞춤형 미션과 예·적금 상품을 추천하는 금융 자산관리 서비스 |

## 2. 프로젝트 기획 배경

최근 개인의 자산 관리와 소비 습관은 경제적 안정과 직접 연결되는 핵심 요소가 되었다. 하지만 많은 사용자는 자신의 금융 데이터를 한눈에 파악하기 어렵고, 지출 패턴을 개선하기 위한 실질적인 행동 지침을 얻지 못한다.

BeBig은 이러한 문제를 해결하기 위해 실제 계좌 데이터와 금융 공공데이터를 결합했다. 사용자는 계좌를 연결해 자신의 총자산과 소비 흐름을 확인하고, 금융 유형 검사를 통해 개인화된 분석 결과를 받을 수 있다. 이후 서비스는 사용자의 자산 상태와 유형에 맞춰 일간·월간 미션을 제공하고, 주거래 은행 및 금융 유형을 고려한 예·적금 상품을 추천한다.

기획의 핵심은 단순한 금융 데이터 조회가 아니라 "데이터를 행동으로 바꾸는 서비스"를 만드는 것이었다. 사용자가 돈을 모으기 위해 무엇을 해야 하는지 구체적으로 안내하고, 미션과 커뮤니티를 통해 지속적인 참여 동기를 제공하는 구조를 목표로 했다.

## 6. Frontend 상세 구현 내용

### 6.1 라우팅 구조

프론트엔드는 도메인별 라우터 파일을 분리했다.

| 라우터 | 담당 화면 |
| --- | --- |
| `router/user.js` | 로그인, 회원가입, 소셜 회원가입, 아이디/비밀번호 찾기 |
| `router/home.js` | 홈, 계좌 목록, 계좌 상세, 계좌 연결, 금융 유형 검사 |
| `router/asset.js` | 자산 분석 |
| `router/mission.js` | 미션 |
| `router/community.js` | 커뮤니티 목록, 작성, 상세 |
| `router/mypage.js` | 마이페이지, 회원정보 수정 |

이 구조를 통해 기능 단위별 화면 확장이 쉬워졌고, 페이지 이동 흐름을 명확하게 관리할 수 있었다.

### 6.2 인증과 API 통신 UX

공통 Axios 인스턴스를 구성해 Pinia의 사용자 Store에서 Access Token을 가져오고, 모든 인증 API 요청에 `Authorization: Bearer {token}` 헤더를 자동으로 붙였다.

응답 인터셉터에서는 401 Unauthorized를 감지하면 사용자 상태를 초기화하고 로그인 페이지로 이동시켰다. 이를 통해 토큰 만료나 인증 실패 상황에서도 사용자가 비정상 화면에 머무르지 않도록 했다.

별도의 `refreshToken` 모듈에서는 Access Token 유효성을 확인하고, 서버에서 새 Access Token을 반환하면 Pinia Store와 LocalStorage에 다시 저장하는 흐름을 구성했다.

### 6.3 반응형 레이아웃

모바일과 PC의 사용 패턴을 다르게 설계했다.

| 환경 | UX |
| --- | --- |
| 모바일 | 상단 Header와 하단 고정 Footer를 사용해 앱처럼 주요 화면을 이동 |
| PC | 상단 WebHeader를 사용해 홈, 미션, 자산분석, 커뮤니티, 마이페이지를 가로 내비게이션으로 제공 |
| 로그인 화면 | 일반 서비스 레이아웃과 분리해 로그인 전환 집중도를 높임 |

Tailwind CSS의 표준 breakpoint를 활용했고, `main.css`에 반복되는 UI 패턴을 공통 클래스로 정의했다. 예를 들어 `section-style`, `button`, `input`, `mission-text`, `community-filter`, `post-content` 같은 클래스를 만들어 페이지마다 일관된 금융 서비스 UI를 유지했다.

### 6.4 홈 대시보드

홈 화면은 사용자가 로그인 직후 자신의 현재 상태를 바로 이해할 수 있도록 구성했다.

구성 요소는 다음과 같다.

| 영역 | UX 의도 |
| --- | --- |
| 사용자 인사 | 로그인 사용자와 게스트 사용자를 분리해 안내 |
| 금융 유형 이미지 | 이미 유형검사를 완료한 사용자는 결과 모달을 볼 수 있고, 미완료 사용자는 검사로 이동 |
| 총자산 요약 | 연결 계좌 잔액을 합산해 총자산 표시 |
| 상위 계좌 2개 | 잔액 기준 주요 계좌를 우선 노출 |
| 계좌 연결 CTA | 계좌가 없을 때 바로 연결 행동으로 유도 |
| 미션 요약 | 월간·일간 미션 상태를 홈에서 바로 확인 |

이 화면은 서비스의 주요 기능인 계좌 연결, 자산 확인, 유형 검사, 미션 수행으로 자연스럽게 이어지는 허브 역할을 한다.

### 6.5 계좌 연결 UX

계좌 연결은 사용자가 가장 민감하게 느낄 수 있는 금융 정보 입력 단계이므로 단계형 UX로 설계했다.

1. 은행 선택 화면에서 은행 로고와 은행명을 그리드로 제공
2. 현재 지원 가능한 은행과 준비 중인 은행을 구분
3. 선택한 은행 정보를 Pinia Store에 저장
4. 은행 로그인 정보를 입력받아 CODEF 연결 API 호출
5. API 요청 중 "계좌를 확인하는 중", "거래 내역을 요청하는 중", "나만의 자산 분석 진행 중"처럼 단계별 로딩 메시지 제공
6. 아이디/비밀번호 오류 발생 시 남은 입력 가능 횟수 안내
7. 연결 성공 시 연결된 계좌 목록, 은행, 계좌번호, 계좌명, 잔액을 표시

이 UX는 CODEF API 응답 대기 시간이 길어질 수 있는 상황에서 사용자의 불안을 줄이고, 현재 어떤 작업이 진행 중인지 알려주는 데 초점을 맞췄다.

### 6.6 계좌 상세 및 거래내역 조회

계좌 상세 화면에서는 거래내역을 한 번에 모두 불러오지 않고 `limit`, `offset` 기반으로 나누어 조회했다. 화면 하단에 가까워지면 다음 페이지를 요청하는 무한 스크롤을 적용했다.

주요 UX는 다음과 같다.

| 기능 | 설명 |
| --- | --- |
| 날짜별 그룹핑 | 거래내역을 날짜 기준으로 묶어 가독성 개선 |
| 입출금 구분 | 출금은 빨간색, 입금은 파란색으로 표시 |
| 잔액 표시 | 거래별 거래 후 잔액을 함께 표시 |
| 새로고침 버튼 | 계좌 거래내역을 CODEF API로 다시 요청 |
| 로딩 상태 | 거래내역 갱신 중 "로딩중" 표시 |

많은 거래내역을 다루는 금융 서비스 특성상, 무한 스크롤과 날짜 그룹핑으로 조회 부담을 줄였다.

### 6.7 금융 유형 검사

금융 유형 검사는 사용자의 소비·저축 성향을 4가지 유형으로 나누기 위한 설문이다.

구현 특징은 다음과 같다.

| 구현 | 설명 |
| --- | --- |
| 질문 랜덤화 | 10개의 유형 질문은 무작위 순서로 표시 |
| 수입 질문 고정 | 월수입 입력 질문은 마지막에 고정 |
| 숫자 검증 | 숫자가 아닌 입력을 감지해 안내 |
| 금액 포맷팅 | 입력 중에도 천 단위 콤마를 적용 |
| 유형 산출 | 두 축의 응답 개수를 비교해 1~4번 금융 유형 결정 |
| 결과 재사용 | 결과 화면을 일반 페이지와 모달 양쪽에서 재사용 |

검사 결과는 금융 유형 이미지, 유형명, 설명, 소비 습관 조언으로 제공된다. 사용자는 홈이나 마이페이지에서 자신의 유형 결과를 다시 확인할 수 있다.

### 6.8 자산 분석 대시보드

자산 분석 화면은 BeBig의 핵심 화면 중 하나다. 연결 계좌와 거래내역을 사용자가 이해 가능한 지표로 변환한다.

#### 총자산 분석

입출금 자산, 예적금 자산, 기타 자산을 나누어 총자산 대비 비율을 가로 막대 형태로 표시했다. 각 영역을 클릭하면 비율과 금액을 툴팁으로 확인할 수 있다.

#### 소비 분석

연도 선택 드롭다운을 제공하고, 해당 연도의 월별 소비 합계를 Chart.js 막대 그래프로 표시했다. 현재 월은 강조 색상으로 구분하고, 월평균 소비액은 빨간 평균선으로 보여준다.

또한 전월 대비 소비 차이를 문장으로 표시해 사용자가 "지난달보다 더 썼는지, 덜 썼는지"를 바로 이해할 수 있게 했다.

#### 금융 상품 추천

상품 추천은 주거래 은행 상품과 다른 은행 상품을 캐러셀로 분리했다.

| 추천 구분 | 설명 |
| --- | --- |
| 주거래 은행 상품 | 사용자의 계좌 기반 주거래 은행에서 예금 2개, 적금 2개 추천 |
| 다른 은행 상품 | 주거래 은행 외 은행 상품을 추천하고 새로고침으로 다른 조합 확인 |
| 상품 정보 | 은행 로고, 상품명, 최고 우대금리, 기간, 홈페이지 링크 제공 |

#### 연령대별 자산 비교

사용자의 연령대를 기준으로 평균 자산과 상위 퍼센트를 표시했다. 삼각형 그래프와 랭크 라인을 사용해 사용자의 위치를 직관적으로 보여준다.

### 6.9 미션 화면

미션 화면은 사용자가 소비 습관 개선을 지속할 수 있도록 게임화 요소를 적용했다.

| 요소 | 설명 |
| --- | --- |
| 월간 달성도 | 현재 미션 달성도를 퍼센트로 표시 |
| 남은 기간 | 이번 달 종료까지 남은 일수 표시 |
| 캐릭터 애니메이션 | 금융 유형별 캐릭터 이미지가 진행률에 맞춰 이동 |
| 월간 미션 | 진행 중, 완료, 실패 상태 표시 |
| 일간 미션 | 체크박스로 완료 처리하고 즉시 달성도 갱신 |

단순한 할 일 목록이 아니라, 진행률과 캐릭터 움직임으로 사용자가 수행 상태를 즉각적으로 느끼도록 구성했다.

### 6.10 커뮤니티 화면

커뮤니티는 금융 정보 공유와 서비스 체류 시간을 늘리는 역할을 한다.

구현 내용은 다음과 같다.

| 기능 | 설명 |
| --- | --- |
| 카테고리 필터 | 예적금, 재테크, 정보공유, 절약팁 |
| 금융 유형 필터 | 꿀벌, 호랑이, 다람쥐, 나무늘보 |
| 정렬 | 최신순, 좋아요순 |
| 페이지네이션 | 페이지 이동 및 현재 페이지 유지 |
| 좋아요 | 목록과 상세에서 좋아요 상태 반영 |
| 프로필 이동 | 작성자 프로필 클릭 시 본인/타인 마이페이지 분기 |
| 이미지 업로드 | 최대 3장 업로드, 미리보기, 삭제 |
| 상세 이미지 모달 | 이미지 클릭 시 확대 보기와 이전/다음 이동 |
| 권한 분기 | 작성자만 수정·삭제 버튼 노출 |

금융 커뮤니티 특성상 정보 탐색성이 중요하므로 필터와 정렬을 명확하게 제공했다. 또한 이미지 업로드와 상세 모달로 사용자가 금융 상품 캡처나 소비 인증 이미지를 공유할 수 있게 했다.

### 6.11 마이페이지

마이페이지는 사용자의 금융 유형, 미션 성과, 커뮤니티 활동을 보여주는 개인 프로필 역할을 한다.

| 기능 | 설명 |
| --- | --- |
| 공개/비공개 설정 | 본인만 공개 상태 변경 가능 |
| 프로필 이미지 | 금융 유형 코드에 따른 캐릭터 이미지 표시 |
| 뱃지 | 지난달 미션 달성도에 따른 뱃지 표시 |
| 뱃지 모달 | 뱃지 기준과 설명 제공 |
| 미션 달성도 | 홈·미션과 동일한 진행률 UI 제공 |
| 작성 글 탭 | 내가 작성한 글 목록 |
| 좋아요 글 탭 | 내가 좋아요한 글 목록 |
| 타 사용자 프로필 | 공개 상태일 때 작성 글과 좋아요 글 조회 |

개인의 미션 성취와 커뮤니티 활동을 함께 보여줌으로써, 자산관리 서비스에 사회적 동기를 더했다.

## 7. PM 관점의 CODEF 금융 데이터 활용 구조

### 7.1 설계 목표

CODEF API를 단순히 계좌 조회에만 사용하는 것이 아니라, BeBig의 핵심 기능인 자산 분석, 거래내역 조회, 미션 생성, 금융 상품 추천의 기반 데이터로 활용하는 구조를 설계했다.

목표는 다음과 같다.

| 목표 | 설명 |
| --- | --- |
| 실제성 | MockData뿐 아니라 실제 계좌와 거래내역을 연결해 서비스 신뢰도 확보 |
| 확장성 | 여러 은행과 여러 계좌를 연결할 수 있는 구조 |
| 재사용성 | 계좌·거래내역 데이터를 자산 분석, 미션, 상품 추천에 재사용 |
| 안정성 | CODEF Access Token 캐싱, RSA 암호화, 중복 계좌 방지, 거래내역 중복 저장 방지 |
| 사용자 경험 | 금융 API 요청 시간이 길어져도 단계별 진행 상태를 프론트에서 안내 |

### 7.2 CODEF 계좌 연결 흐름

```text
사용자
  ↓ 은행 선택 및 은행 로그인 정보 입력
Frontend
  ↓ POST /home/account/add
Backend
  ↓ JWT에서 userId 추출
  ↓ user_connected_id 존재 여부 확인
CODEF
  ↓ connectedId 신규 생성 또는 기존 connectedId에 은행 계정 추가
CODEF
  ↓ 계좌 목록 조회
Backend
  ↓ account 테이블에 계좌 저장
  ↓ 거래내역 조회 요청
CODEF
  ↓ 거래내역 반환
Backend
  ↓ transaction 테이블에 거래내역 저장
  ↓ 자산·유형 조건 충족 시 미션 생성
Frontend
  ↓ 연결 성공 계좌 목록 표시
```

### 7.3 CODEF 관련 주요 데이터 구조

| 테이블/데이터 | 역할 |
| --- | --- |
| `user.user_connected_id` | CODEF ConnectedId 저장 |
| `account.account_num` | 연결 계좌 번호 |
| `account.bank_id` | 은행 식별자 |
| `account.account_name` | 계좌명 |
| `account.account_type` | 입출금, 예적금, 기타 등 계좌 유형 |
| `bank.bank_code_codef` | CODEF 요청에 필요한 은행 기관 코드 |
| `transaction.account_num` | 거래내역이 속한 계좌 |
| `transaction.transaction_balance` | 거래 후 잔액 |
| `transaction.transaction_amount` | 거래 금액 |
| `transaction.transaction_date` | 거래 일시 |
| `transaction.transaction_type` | 입금 또는 출금 |
| `transaction.transaction_vendor` | 거래처명 |
| `codef_token.access_token` | CODEF API Access Token 캐싱 |
| `codef_token.token_expiry_time` | CODEF Token 만료 시간 |

이 구조 덕분에 CODEF에서 받은 실제 금융 데이터를 서비스 내부 도메인에 맞게 저장하고, 여러 기능에서 재활용할 수 있다.

### 7.4 CODEF 인증 및 보안 흐름

CODEF API 요청은 민감한 금융 인증 정보를 다루므로 다음 흐름으로 구성되어 있다.

1. CODEF OAuth Token을 발급받는다.
2. 발급받은 Access Token과 만료 시간을 DB에 저장한다.
3. API 요청 전 기존 Token이 유효하면 재사용한다.
4. 만료되었으면 새 Token을 발급받아 DB를 갱신한다.
5. 사용자가 입력한 은행 비밀번호는 CODEF RSA Public Key로 암호화해 전송한다.

이를 통해 CODEF API 호출 비용과 인증 부담을 줄이고, 민감한 비밀번호를 평문으로 외부 API에 전달하지 않도록 설계했다.

### 7.5 거래내역 저장 및 중복 방지

거래내역 저장 흐름은 다음과 같다.

1. 계좌번호로 은행 ID를 찾는다.
2. 은행 ID로 CODEF 은행 코드를 찾는다.
3. 사용자의 ConnectedId와 계좌번호, 은행 코드를 사용해 거래내역을 요청한다.
4. CODEF 응답의 거래처, 잔액, 입금액, 출금액, 거래일시를 `TransactionVo`로 변환한다.
5. 기존 거래내역과 `거래일시 + 거래금액` 기준으로 비교한다.
6. 중복되지 않는 거래만 batch insert한다.
7. 거래내역이 없는 계좌는 현재 잔액 기반의 임시 거래내역을 생성해 자산 분석이 가능하도록 한다.

이 구조는 계좌를 다시 갱신하거나 배치가 반복 실행되어도 같은 거래가 계속 누적되는 문제를 줄이기 위한 의사결정이다.

### 7.6 배치 기반 데이터 갱신 구조

Spring Batch와 Quartz를 사용해 금융 데이터와 미션 데이터를 주기적으로 갱신한다.

| Job | 역할 | 스케줄 |
| --- | --- | --- |
| `transactionUpdateJob` | 연결된 모든 계좌의 거래내역 갱신 | 8시간 간격 |
| `assignDailyMissionJob` | 전체 사용자 일간 미션 갱신 | 매일 00:00 |
| `updateMonthlyMissionJob` | 월간 미션 변경 및 지난달 점수 저장 | 매월 1일 00:00 |
| `dailyCheckMonthlyMissionsJob` | 일부 월간 미션의 매일 성공 여부 확인 | 매일 23:50 |
| `checkEndOfMonthMissionsJob` | 월말 기준 월간 미션 성공 여부 확인 | 매월 말일 23:50 |
| `ageUpdateJob` | 사용자 나이 갱신 | 매년 1월 1일 |

PM 관점에서 이 구조는 서비스가 사용자의 행동을 수동 조회에만 의존하지 않고, 시간이 지나며 자동으로 최신 상태를 반영하도록 만드는 핵심 운영 설계다.

## 8. 금융 상품 추천 구조

상품 추천은 금융 공공데이터 기반 예금·적금 상품 데이터를 DB에 저장하고, 사용자 계좌와 금융 유형을 기준으로 추천한다.

추천 로직의 주요 기준은 다음과 같다.

| 기준 | 설명 |
| --- | --- |
| 주거래 은행 | 사용자의 계좌 중 가장 많이 연결된 은행을 주거래 은행으로 판단 |
| 최고 우대금리 | 예금·적금 상품을 최고 우대금리 기준으로 우선 추천 |
| 금융 유형 | 사용자의 금융 성향에 따라 상품 기간 기준을 함께 고려 |
| 은행 다양성 | 주거래 은행 상품과 다른 은행 상품을 분리해 비교 가능하게 제공 |

프론트에서는 이를 주거래 은행 상품과 다른 은행 상품 캐러셀로 분리했다. 사용자는 자신이 이미 거래 중인 은행 상품과 다른 은행의 대안을 함께 비교할 수 있다.

## 9. 미션 개인화 구조

BeBig의 미션은 단순 랜덤 미션이 아니라 사용자의 계좌 연결 상태, 금융 유형 검사 상태, 월수입, 거래내역, 커뮤니티 활동과 연결된다.

### 미션 생성 조건

사용자가 다음 조건을 만족하면 개인화 미션이 생성된다.

1. 금융 유형 검사를 완료했다.
2. CODEF 계좌 연결을 완료했다.
3. 사용자에게 기존 일간 미션이 없다.

### 일간 미션

일간 미션은 매일 3개씩 제공된다. 사용자가 체크박스를 클릭하면 완료 상태가 변경되고, 월간 미션 점수도 갱신된다.

### 월간 미션

월간 미션은 순환 구조로 운영된다. 일부 미션은 매일 성공 여부를 확인하고, 일부 미션은 월말에 최종 성공 여부를 확인한다.

예시 기준은 다음과 같다.

| 미션 유형 | 판단 데이터 |
| --- | --- |
| 예적금 계좌 추가 | `account_type = 12` 계좌 수 변화 |
| 커뮤니티 글 작성 | 월간 게시글 수 |
| 좋아요 획득 | 월간 좋아요 합계 |
| 소비 목표 | 거래내역 기반 소비 변화 |
| 저축 목표 | 월초 잔액과 현재 잔액 차이 |
| 일간 미션 수행 | 완료된 일간 미션 수 |

이 구조는 사용자의 실제 금융 데이터와 서비스 내 활동 데이터를 함께 사용해 실천 가능한 자산관리 루틴을 만드는 데 초점을 둔다.

## 10. UX 의사결정과 문제 해결

### 문제 1. 금융 API 연결은 응답 시간이 길고 사용자가 불안해할 수 있음

해결:

- 계좌 연결 요청 중 단계별 로딩 메시지를 제공했다.
- "계좌를 확인하는 중", "거래 내역을 요청하는 중", "나만의 자산 분석 진행 중"처럼 사용자가 현재 진행 단계를 이해할 수 있게 했다.
- 은행 아이디·비밀번호 오류 시 오류 내용을 alert로 표시하고 남은 입력 횟수를 안내했다.

### 문제 2. 거래내역은 데이터량이 많아 한 번에 렌더링하면 부담이 큼

해결:

- 백엔드 API는 `limit`, `offset` 기반 페이지네이션을 제공한다.
- 프론트는 스크롤 하단 접근 시 다음 페이지를 불러오는 무한 스크롤을 적용했다.
- 거래내역은 날짜별로 그룹핑해 사용자가 시간 흐름을 쉽게 읽게 했다.

### 문제 3. 금융 데이터는 숫자 중심이라 사용자가 의미를 해석하기 어려움

해결:

- 총자산을 자산 유형별 비율 바와 툴팁으로 표현했다.
- 소비 분석은 월별 막대 그래프와 평균선을 같이 보여주었다.
- 전월 대비 소비 차이를 문장으로 변환했다.
- 연령대 평균 자산과 상위 퍼센트를 시각화했다.

### 문제 4. 자산관리 서비스는 재방문 동기가 약할 수 있음

해결:

- 일간·월간 미션을 제공했다.
- 미션 달성률을 진행바와 캐릭터 애니메이션으로 표현했다.
- 지난달 달성도 기반 뱃지로 성취감을 제공했다.
- 커뮤니티와 프로필 공개 기능으로 사용자 간 상호작용을 만들었다.

### 문제 5. 로그인 전 사용자가 서비스를 경험하지 못하면 이탈할 수 있음

해결:

- 게스트 로그인을 제공했다.
- 게스트 사용자는 홈과 일부 탐색을 경험할 수 있고, 계좌 연결·마이페이지 등 민감 기능은 로그인 안내로 분기했다.

## 14. 포트폴리오 발표용 설명

### 프로젝트 소개

BeBig은 실제 계좌 데이터와 금융 공공데이터를 활용해 사용자의 자산 상태를 분석하고, 소비 습관 개선을 위한 개인화 미션과 예·적금 상품 추천을 제공하는 금융 자산관리 서비스입니다. 단순 조회 서비스가 아니라 사용자의 금융 데이터를 행동으로 연결하는 것을 목표로 했습니다.

### 내가 맡은 역할

저는 Frontend 개발과 PM을 담당했습니다. Frontend에서는 Vue 3와 Tailwind CSS를 활용해 홈 대시보드, 계좌 연결, 거래내역 조회, 자산 분석, 미션, 커뮤니티, 마이페이지 화면을 구현했습니다. PM으로서는 프로젝트의 기능 우선순위와 의사결정을 담당했고, CODEF API를 활용해 실제 계좌와 거래내역을 서비스 내부 데이터 구조로 연결하는 흐름을 설계했습니다.

### 가장 중요한 기여

가장 중요한 기여는 실제 금융 데이터를 사용자 경험과 연결한 점입니다. CODEF API로 받은 계좌와 거래내역은 단순히 목록으로 보여주는 데서 끝나지 않고, 총자산 분석, 월별 소비 분석, 금융 상품 추천, 개인화 미션 생성에 사용됩니다. 프론트에서는 이 데이터를 차트, 진행률, 카드, 캐러셀, 모달 등의 형태로 변환해 사용자가 현재 상태와 다음 행동을 쉽게 이해하도록 만들었습니다.

### 배운 점

금융 서비스는 데이터 정확성뿐 아니라 사용자가 안심하고 이해할 수 있는 흐름이 중요하다는 점을 배웠습니다. 특히 계좌 연결처럼 민감한 과정에서는 단계별 안내와 명확한 오류 메시지가 필요했고, 거래내역처럼 데이터가 많은 화면에서는 성능과 가독성을 함께 고려해야 했습니다. PM 역할을 통해 기능을 많이 만드는 것보다 핵심 데이터가 어떤 사용자 가치로 이어지는지 설계하는 것이 중요하다는 것도 배웠습니다.

## 15. 면접 예상 질문과 답변

### Q1. 이 프로젝트에서 가장 핵심적인 기능은 무엇인가요?

핵심 기능은 CODEF API를 활용한 실제 계좌 연결과 이를 기반으로 한 자산 분석입니다. 사용자가 계좌를 연결하면 계좌 목록과 거래내역을 저장하고, 이 데이터를 총자산 분석, 소비 분석, 미션 생성, 금융 상품 추천에 활용합니다. 단순한 계좌 조회가 아니라 금융 데이터를 서비스 전반의 개인화 기능으로 확장한 것이 핵심입니다.

### Q2. Frontend에서 가장 신경 쓴 UX는 무엇인가요?

계좌 연결 UX와 자산 분석 UX를 가장 신경 썼습니다. 계좌 연결은 민감한 금융 정보 입력 단계라 사용자가 불안할 수 있기 때문에 은행 선택, 로그인 입력, 단계별 로딩 메시지, 오류 횟수 안내, 연결 성공 결과를 분리했습니다. 자산 분석에서는 숫자 데이터를 그대로 보여주기보다 비율 바, 소비 차트, 평균선, 전월 대비 문장, 상품 추천 캐러셀로 변환해 사용자가 빠르게 이해하도록 했습니다.

### Q3. 거래내역 화면에서 무한 스크롤을 사용한 이유는 무엇인가요?

거래내역은 계좌별로 수백 개 이상 존재할 수 있어 한 번에 모두 불러오면 초기 로딩과 렌더링 비용이 커집니다. 그래서 백엔드의 `limit`, `offset` API와 연동해 일정 개수만 먼저 불러오고, 사용자가 스크롤을 내릴 때 다음 거래내역을 추가로 요청하도록 구현했습니다. 동시에 날짜별 그룹핑을 적용해 많은 거래내역도 읽기 쉽게 구성했습니다.

### Q4. PM으로서 CODEF API 구조를 어떻게 설계했나요?

사용자가 은행 정보를 입력하면 백엔드에서 JWT로 사용자 ID를 식별하고, 사용자의 CODEF ConnectedId 존재 여부를 확인합니다. 없으면 ConnectedId를 새로 생성하고, 있으면 기존 ConnectedId에 은행 계정을 추가합니다. 이후 계좌 목록을 조회해 account 테이블에 저장하고, 각 계좌의 거래내역을 요청해 transaction 테이블에 저장합니다. 저장된 데이터는 자산 분석, 미션, 상품 추천에서 재사용되도록 설계했습니다.

### Q5. 인증 처리는 어떻게 구성했나요?

프론트에서는 Pinia Store와 LocalStorage에 Access Token과 Refresh Token을 저장했습니다. Axios 요청 인터셉터에서 Access Token을 Authorization 헤더에 자동으로 넣고, 응답 인터셉터에서 401 응답이 오면 로그아웃 처리 후 로그인 화면으로 이동시켰습니다. 일부 API 호출 전에는 Refresh Token 확인 모듈을 통해 Access Token 유효성을 검증하고 새 토큰을 저장하도록 구성했습니다.

### Q6. 이 프로젝트에서 아쉬운 점과 개선 방향은 무엇인가요?

현재 은행명과 이미지 매핑이 여러 화면에 중복되어 있어 공통 유틸 함수나 매핑 모듈로 분리하면 유지보수성이 좋아질 수 있습니다. 또한 CODEF API 연결 가능 은행을 확장하고, 상품 추천 알고리즘을 사용자의 실제 저축 목표, 위험 선호도, 만기 선호도까지 반영하도록 개선할 수 있습니다. 자산 분석 화면에서는 더 많은 기간 비교와 카테고리별 소비 분석을 추가하면 사용자가 더 구체적인 소비 개선 전략을 얻을 수 있습니다.
